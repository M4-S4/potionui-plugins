# Preset Editor: reference

The whole of what Preset Editor does, its limits, where it keeps its files and its settings. The [README](https://github.com/M4-S4/potionui-plugins/blob/main/preset-editor/README.md), also in Admin › Documentation as "Preset Editor", gives the short version.

## What you can do

- **New Preset** (header of Admin → Presets, or the Preset Editor page): either copy a preset of the catalogue, or start from a blank skeleton (engine, category, modes, a cloud driver, or a native model family whose standard chain is wired from the pipe catalogue). Give it a name, the folder `content/presets/local/<Model>/<variant>` and optionally an id; the id is otherwise generated like the ids of the presets PotionUI ships. From the Admin header, "Publish right away" publishes the copy as it is and opens it there.
- **Edit…** (same header) lists the local presets and opens one as a draft; publishing writes it back over its folder, and the previous version goes to the history.
- The draft workbench lists the files, opens any YAML, Markdown, JSON or text file in a text editor with line numbers, insertable fragments (a `_shared` options file, the standard native chain, a `@loop` block, the cloud chain, a field) and a save that refuses to overwrite a file changed elsewhere. Modes are added from the skeleton or removed.
- `preset.yml` opens as a form: name, version, category, engine, driver and tags as fields, the advanced sections (`vars`, `configuration`, `llm`, `speed_profiles`, `formulas`, `requires`, `requirements`, `prompt_resources`, `prompt_syntax`, `negative_prompt`) as YAML, `id` and `schema` read-only. Saving rewrites only the keys you changed, keeps the rest of the file as it is, and asks before dropping a comment inside a rewritten section. The YAML view edits the whole file.
- The Media view uploads the cover and the gallery examples (images are downscaled to 1024 px WebP as PotionUI does for style previews, videos are stored as they are), declares them in `media:` with a caption, a mode, a seed and a prompt, reorders the gallery, picks a cover among the files already there and deletes files. `description.md` has a Markdown preview built by a copy of the core's `processMarkdown`, the renderer of Admin → Presets, with the same HTML and classes: a single line break stays a line break, headings stop at `###`, GFM tables are tables, and an image line appears as its `!` and its link, since PotionUI shows no image in a description. Links follow the rule of PotionUI 0.2.0: an `http`, `https` or `mailto` link is a link, and so is a relative target that starts with `/`, `./`, `../`, `#` or `?`; anything else (`javascript:` or `data:`, even written with HTML entities, `//host`, a bare `docs/guide.md`) stays text.
- `form.yml`, `tabs/*.yml` and the fragments under `files/` open in a builder: the field tree (drag and drop, containers, tabs and includes backed by files), a palette of every field type this instance knows, an inspector for the attributes PotionUI's schema defines (typed default, width, audience, flags, formula group, the type's own configuration keys, option lists, `_shared` option files, the vars of an include) and raw YAML for the rest (`when`, `reactions`, …). What the core would refuse shows before saving. Form settings (label, description, prompt, prompt label and placeholder, assistant guide, examples, default variant, order, `negative_prompt`, `requirements`, `segment_templates`) and new variants (`variants/<name>/form.yml`) are edited there too. Saving rewrites the whole file, so its comments go away; the YAML view keeps them.
- `pipeline.yml` opens in a builder too: the ordered pipe list, the pipe catalogue of this instance, inputs as `[input, source pipe, output]` triples checked against the catalogue (a source must come earlier in the list, its output must exist and match the input's type), each pipe's declared configuration keys with their choices, Jinja values kept as text, and two start chains (a native family, cloud). Once the preset is published, the form preview can render the pipeline with the form's current values through PotionUI's own pipeline builder, which needs every value the pipeline reads, models included. A mode whose `pipeline.yml` is the single line `pipeline_from: <mode>` (PotionUI 0.2.0: it runs the pipeline of that sibling mode with its own form) opens read-only: the builder names that mode and opens its `pipeline.yml`, and never writes the file. To give such a mode a pipeline of its own, replace the line in the YAML view. A mode that another mode names this way cannot be removed until that other mode points elsewhere.
- **Download zip** on a draft, and the `zip` button of each local preset in the Edit… menu, give the folder as an archive. **Import zip** turns such an archive, or any zipped preset folder with `preset.yml` at its root, into a draft: every entry is checked before anything is written (no path escape, no link, no backslash, caps on size and count, allowed extensions only), then the draft is linted.
- A draft shows its lint report; **Publish** needs a report without errors, writes the preset atomically, reloads the catalogue and checks that PotionUI loads it. When the loader refuses the preset (the linter does not check everything, field types for one), the previous state is put back and the loader's messages are shown. By default a published preset is installed on the instance; assigning it to users and groups stays in Admin → Presets, as for any preset. Once published, the form of each mode can be previewed in the workbench with PotionUI's own form renderer.
- **History** lists the versions kept when a local preset was published over or deleted; **Restore** opens one as a draft. **Delete** uninstalls a local preset and moves its folder to the history.

## Limits worth knowing

- The form and pipeline builders rewrite the whole file they save: comments and the original formatting go away (the YAML view keeps them, and the `preset.yml` form rewrites only the sections you change). Every attribute a builder does not show is kept as raw YAML.
- A fragment with `{{ vars.name }}` placeholders is checked by the builder as a fragment; the core's lint, run on every save, tells whether each include gives it the vars it needs.
- The form preview and the rendered pipeline exist only for a published version, and the pipeline renders only when every form value it reads is filled in, models included.
- The description preview applies the link rule of PotionUI 0.2.0 on every core. On PotionUI 0.1.0, Admin → Presets still links a bare relative target such as `docs/guide.md` or `//host`, which the preview shows as text.
- The pipeline builder checks the `pipeline_from` line as the core does, except a pointer to a mode that is itself a pointer: the core's lint, run on every save, reports that one.
- Media uploads are capped at 20 MB and limited to PotionUI's own extensions (`.jpg`, `.jpeg`, `.png`, `.webp`, `.gif`, `.mp4`, `.webm`; no SVG). Images become 1024 px WebP. Draft media are fetched whole before they show, videos included.
- A zip import is unpacked only after every entry passed the checks (64 MB archive, 256 MB unpacked, 2000 entries, no link, no path escape, text and media files only).
- The linter does not check field types: a preset that lints clean but uses a `type:` the loader refuses is rolled back at publish time, with the loader's messages.
- Preset ids are generated like PotionUI's own (ULID) unless you set one; a published id must be free across every scanned root, marketplace included, because the loader keeps the first preset it finds for an id.

## Where things live

- Published presets: `content/presets/local/<Model>/<variant>/`, the user-owned preset root PotionUI scans and backs up. In Docker, mount that folder as a volume: the official image only mounts `/app/models` and `/app/storage`, so a published preset would otherwise vanish when the container is recreated.
- Drafts and history: `storage/plugins/preset-editor/`. They are not part of the core backup.
- A transient staging area, `content/presets/.preset-editor/staging/`, is emptied when the application starts.

## Settings

In Admin → Plugins → Preset Editor → Settings:

- **Versions kept per preset** (default 10).
- **Install a published preset on this instance** (on by default; the publish dialog can override it each time).
