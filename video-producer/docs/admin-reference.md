## Requirements

- PotionUI 0.2.0 or later, which holds the plugin API for image vectors and faces (`detect_faces`, `embed_faces`: PotionUI/PotionUI#58), with plugins enabled, and an admin account to enable this one.
- At least one video engine: the native engine on this machine, a Remote Native worker, or a cloud provider with a video model. See Engines below.
- At least one Video Director preset, installed and assigned to the users who will generate: Wan, LTX, MiniMax-H3 or a cloud video preset. See Models and presets below.
- The model files that these presets need, downloaded. Video Producer picks them itself from the recommendations of each preset (see Generation › Required models); a preset with a missing file is blocked for generation.
- The SeedVR2 preset and its model files, assigned to the users, to turn a chosen draft take into a final. A take of the base MiniMax-H3 preset is enlarged by the upscale mode of its own preset instead. The RTX Upscale preset of the NVIDIA RTX Upscale plugin can enlarge a take too, in seconds and without adding detail, once the server has the `nvidia-vfx` package (see RTX Upscale for finals).
- Optionally, for a guided final, the LTX-2.5 preset with its model files and the Layout-To-Render IC-LoRA (`ltx-2.5-22b-ic-lora-layout-to-render-1.0.safetensors`, 1.22 GB, from `Lightricks/LTX-2.5-22b-IC-LoRA-Layout-To-Render` on Hugging Face), assigned to the users. See Generation › Final takes in **Video Producer: technical reference**.
- Optionally, for the Ref2VA profile on LTX-2.5, the Ingredients IC-LoRA (`ltx-2.5-22b-ic-lora-ingredients-0.9.safetensors`, 1.31 GB, from `Lightricks/LTX-2.5-22b-IC-LoRA-Ingredients` on Hugging Face, whose access the administrator accepts with their own account) next to the LTX-2.5 files. See Generation › The reference sheet (Ref2VA on LTX-2.5) in **Video Producer: technical reference**.
- ffmpeg and ffprobe on the PotionUI server, to deliver a video file and to extract a frame of a take at a given time. See ffmpeg below.
- For a local engine, a GPU that meets PotionUI's own Hardware Requirements page: a Turing or newer NVIDIA card, driver 580 or newer, 8 GB of VRAM and 16 GB of system RAM as the supported minimum, 16 to 24 GB of VRAM and 32 GB of RAM recommended. Video families need more than the floor; that page has a verdict per family. What Video Producer measured on a 12 GB card, and the system RAM it needs, is under Hardware.
- For a cloud engine, an account and an API key with the provider (OpenRouter or Google AI Studio).
- For the assistant, a language model configured in PotionUI (Admin → LLM / Assistant) and assigned to the users, able to call tools. A local llama.cpp `llama-server` (added as an OpenAI configuration) is recommended when the model shares the video card; Ollama works once its context size, keep-alive and thinking mode are set; an online provider such as OpenAI is possible too. The Native client is not recommended on a 12 GB card. See The assistant mode › Which language model.
- The `jsonschema` Python package, which checks the project documents. The plugin relies on it; the PotionUI image already contains it, and its version is pinned in `constraints.txt`. There is nothing to install.

## Hardware

The measures behind the figures below are under Bench measures in **Video Producer: technical reference**.

What to plan for:

- **8 GB of VRAM.** Install and assign the two 8 GB presets, **Wan 2.1 T2V 1.3B (8 GB)** and **Wan 2.2 TI2V 5B (8 GB)** (see Hardware tiers): text to video in 480p, and image to video for the 5B, with 32 GB of system RAM.
- **12 GB of VRAM.** For MiniMax-H3, install and assign the two 12 GB presets (see Hardware tiers, and Bench measures in **Video Producer: technical reference** for the run without them). For Wan 2.2 14B, install and assign **Wan 2.2 14B Lightning (12 GB)** for text to video in 6 steps and its companion **Wan 2.2 14B Lightning I2V (12 GB)** (recipe `vp-wan22-14b-lightning-i2v-12gb`), so that a shot that starts from an image (its own first frame, or the last image of the previous shot) runs image to video in 4 steps without changing its engine, or the core Wan 2.1 / 2.2 preset with its image-to-video pair (recipe `vp-wan22-14b-i2v`); the 30-step text to video of the core preset runs too, slowly (see Hardware tiers). The estimate warns before the user starts: it announced 37.1 GB for Wan and between 41.75 and 42.85 GB for the 12 GB presets against a budget of 10 GB, with the warning "Will stream through host RAM, slower" and no block.
- **System RAM.** Plan on 32 GB for the 8 GB presets and on 64 GB for the 12 GB presets and for Wan 2.2 14B: the MiniMax-H3 presets stream their text encoder from system RAM (the `text_encoder_placement` option), the part of the DiT that does not fit on the card stays there too, and Wan 2.2 14B holds about 35 GB of process memory. Each preset declares its figure in `requires.min_ram_gb`, shown as a badge in the preset picker.
- **Time.** On this card a 5-second draft takes about 6 to 7.5 minutes with the MiniMax-H3 12 GB presets, about 3.5 minutes with Wan 2.2 14B Lightning, about 5.5 minutes in image to video with 6 steps and about 26 minutes with the 30 steps of the core Wan preset, and a final by SeedVR2 upscale to 1080p takes more than two hours. Tell your users, and set **Max generations in flight per user** and the monthly GPU minutes with this in mind.
- **After an out-of-memory error.** If every take fails within seconds after a CUDA out of memory error, see Troubleshooting.
- **The assistant.** When its model shares the video GPU, unload it before a generation: see The assistant mode › Which language model.
- **Disk.** The Wan starter recipe downloads about 35.6 GB; the SeedVR2 files are listed under SeedVR2 for finals.

## Install and activate

In Admin → Plugins, enable **Video Producer**. A **Video Producer** entry appears in the sidebar; it opens the page `/plugins/video-producer`. The plugin keeps its own database tables (`video_producer_*`): they hold the projects, the takes, the time measures and the video exports (see Projects and media › Tables, Generation › Tables and Exports › Tables in **Video Producer: technical reference**). A background task follows running generations (see Generation › Following the takes in **Video Producer: technical reference**); another one works through the queue of video exports (see Exports › The assembled video in **Video Producer: technical reference**).

Until its setup steps are done, Admin → Plugins shows a **Setup needed** badge on the plugin: open its Overview tab and follow its **Setup** section, which links to the administration page, **Video Producer: administration**. The same page is under Admin → Documentation as **Video Producer: administration**. The user guide is in the **User Guide** section of the Documentation page that every signed-in user sees, as **Video Producer: user guide**.

- A check that cannot read the state of the instance shows as a step still to do. If a check itself fails, PotionUI shows its own text, "This step could not be checked. See the server log."

## Settings

In Admin → Plugins → Video Producer → Settings:

- **Draft resolution** (`draft_resolution`, default 832×480): the size of draft takes: 832×480, 960×544 or 1280×720. For a native preset, a draft is made at this size, turned to the orientation of the sizes the preset makes the film in, when the preset offers it among them; otherwise the one of them closest in area is used (see Generation › Formats and sizes in **Video Producer: technical reference**). A project can choose another size per preset (`engine.sizes`), which this setting then no longer sets. A cloud model uses its own resolution (see Generation › Formats and sizes in **Video Producer: technical reference**). The final quality and a re-render use the largest of those sizes of the preset, or the largest resolution of the model, whatever this setting says. It does not set the frame rate: a take keeps the frame rate of its preset (see Generation › The frame rate of the takes in **Video Producer: technical reference**).
- **Max generations in flight per user** (`max_parallel_jobs`, default 2): how many takes of one user PotionUI holds at once, whether running or waiting in its own queue, across all the projects of that user. Takes past that number stay **Queued** in Video Producer, with no PotionUI generation yet, and the follow-up task hands them over in the order of the queue as soon as a place frees up. A waiting take already reserves its GPU minutes when its user's minutes are limited. See Quotas, and Generation › Following the takes in **Video Producer: technical reference**.
- **Export cache per user (MB)** (`export_dir_quota_mb`, default 2048): the size budget of each user's export folder (`video_producer/exports/<user id>/` in the file storage directory), where the exported videos and stems are kept. It is per user, not for the whole instance, and it is checked when an export is requested. See Exports › Storage and quota in **Video Producer: technical reference**.
- **Versions kept per project** (`versions_kept`, default 50): how many saved versions each project keeps, from 5 to 500. When a project goes over it, the oldest versions are deleted. See Projects and media below.

The first one is a choice between three values; the other three are numbers. Values are saved as text, and the form itself does not enforce a minimum or a maximum, so the plugin applies its own bounds: 1 to 16 parallel generations, 1 to 1,048,576 MB of export budget and 5 to 500 versions. A number outside its range is brought back to the nearest bound; an empty value, or one that is not a whole number, falls back to the default.

The language is not a setting here: each user chooses it (see chapter 15, Language, in **Video Producer: complete reference**). The language of the prompts is not a setting at all: every prompt is in English (see Projects and media › The document in **Video Producer: technical reference**).

## Quotas

Admin → Users → Plans can limit one thing for this plugin: **Video Producer GPU minutes per month** (`video-producer.gpu_minutes`). It is a count in minutes, in a monthly window. To use it:

1. Open Admin → Users → Plans and open a plan you created. The built-in plans cannot take new limits: their **Add limit** button is disabled.
2. Click **Add limit** and pick **Video Producer GPU minutes per month**.
3. Enter the number of minutes, then assign the plan to groups or users in the same editor.

A plan without this limit means unlimited minutes. The **Admins are exempt** switch in the plans list applies as usual. For a user without a limit and for an exempt admin, Video Producer reserves, adjusts and refunds no minute: nothing is recorded in the ledger for their takes, so a limit that you add later counts only what is recorded from then on.

How it is applied:

- Video Producer applies the limit itself, when a take is created. PotionUI does not count these minutes on its own: the plugin records them in the usage ledger of the limit, and the limit's total is the sum of what it recorded in the month.
- **Reservation.** Each native take of a user whose minutes are limited (a plan limit, and not an exempt admin) reserves minutes before it is stored, even while it waits for a free place (`max_parallel_jobs`): `generation.create` records them in the ledger under the reference of the take to come, then inserts the row with `units_reserved` already set. When PotionUI cannot record them, the request ends with the block `quota_unrecorded` and nothing is stored (the deck shows **Try again**); when the insertion itself fails, the reservation is refunded before the error goes up. A request that makes several takes (`generate`, the final pass, the candidates of start and end images) is refused as a whole (`whole_batch`): when one take cannot reserve its minutes, the takes already created are refunded and deleted before the block is raised. The reservation is the measured time of the preset, backend and resolution when there is one (see Generation › Time calibration in **Video Producer: technical reference**), otherwise 10 seconds of GPU work for every second of video: a 5-second shot reserves about 0.83 minute.
- **Check.** The estimate that the production deck shows before generating includes the quota (`quota.needed_minutes` against `quota.remaining`). When it is not enough, Generate selection is refused with the block `quota_exceeded`, and the server applies the same check to a generation, a final and a retry, whatever the page says. Of the three things the estimate measures (time, memory, quota), only the quota blocks: not enough memory only warns. A plan without a limit, and an exempt admin, are never blocked; their takes keep `units_reserved` at 0, and their end neither adjusts nor refunds anything.
- **Adjustment.** When a take that reserved minutes ends, its reservation is brought to the real duration of the generation: if it ran longer, the difference is recorded on top (reference suffixed `:adjust`); if it ran shorter, the reservation is refunded and, only when that refund went through (`refund_limit_event` answers a count above 0), the real duration is recorded (reference suffixed `:actual`); when the refund fails, a warning is logged and the reservation stays as it was, so that the take is never counted twice.
- **Refund.** A take that fails, is cancelled or is refused by PotionUI gets its whole reservation back, if it had one. Deleting a take cancels it first when it is in flight, and deleting a project cancels its takes in flight and refunds their reservations before it deletes the rows.
- A generation that is already running is never stopped by a quota; only the next ones are refused.
- Cloud engines do not use GPU minutes (`quota.applies` is false, the reservation is 0). Their spending belongs to the PotionUI limit **Cloud spend per month** (`cloud_spend_usd_month`), which you add to a plan in the same way.

## Engines

Video Producer offers the engines that you enabled for it:

- **This machine** (`native.local`): the native engine of the PotionUI server, always present. Nothing to add; check that it is enabled in Admin → Backends.
- **Studio server** (`native.remote`): a Remote Native backend, that is another machine or rented compute that runs a PotionUI Remote Native worker. In Admin → Backends add a Remote Native backend and paste the URL of the worker, or provision one from the backend's Infrastructure tab. The model files must also be on the worker; the backend's Models tab shows the exact per-file paths. The Remote Native documentation describes the worker.
- **Cloud**: the presets **OpenRouter Video** and **Gemini Video**. Install the `openrouter-provider` or the `google-gemini-provider` plugin, add its backend with your API key ("Add an OpenRouter backend with your API key" or "Add a Google Gemini backend with your AI Studio API key" in that plugin's setup), then turn on a video model in the backend's Catalog tab. Each shot is one paid request to the provider.

ComfyUI is not offered as an engine. Video Producer builds one Video Director document per shot, and a ComfyUI preset does not run Video Director documents: it keeps its own per-batch prompt relay.

What the **Generation engine** pop-up of the production deck lists, for a given user:

- Under the highest-priority enabled native backend (This machine or a Studio server), each Video Director preset that is assigned to the user. A MiniMax-H3 preset is shown as **MiniMax H3**, **MiniMax H3 Fast** or **MiniMax H3 VDN (experimental)**. A native backend that PotionUI reports as configured with no GPU (its device is `cpu`) is not an engine: `GET /me` leaves it out of `engines`.
- Without any native backend (a cloud-only instance), the native presets are not offered, and neither is anything that runs on one: `features.upscaler`, `features.upscalers`, `features.interpolators`, `features.guided` and `features.sheet` are all off, the final windows say why ("SeedVR2, RTX Upscale, the interpolators and the guided render run on a native backend of this instance, and none is enabled…"), and the server refuses an upscale or a guided final with the block `no_native_engine` before any take is created or any GPU minute reserved.
- When the highest-priority native backend is a Studio server, the RTX pipes run on its worker, whose Python packages this server cannot see: `GET /me` then offers RTX Upscale and NVIDIA Frame Generation without checking `nvidia-vfx` here (`features.upscalers.rtx_checked` and `features.interpolators.rtx_checked` are `false`), the final windows say so, the automatic choices prefer what was checked (SeedVR2, then RIFE) and take RTX only when nothing else is ready, and a take that needs a package the worker lacks fails there with the worker's error.
- Under each enabled cloud backend, each video model turned on in its catalog, by the name of the model. A cloud model runs through the cloud preset whose driver (`cloud.openrouter` or `cloud.google`) matches the backend.

The routing of a native take belongs to PotionUI: Video Producer submits the request of the preset and PotionUI chooses the backend that runs it, by its own priority and eligibility rules. The take records the backend it ran on (`backend_id`), and the take card shows it. The pop-up does not pin a take to a backend.

The choice is saved with the project (`engine.backend`, `engine.preset` and, for a cloud model, `engine.model`), and so is the Draft and Final control of the deck (`engine.quality`, `draft` or `final`), which the deck takes again when the project opens (see Projects and media › The document in **Video Producer: technical reference**). The Settings drawer of the production deck, where the user sets the engine, the profile, the sizes and the drafts, is described in chapter 8 of **Video Producer: complete reference** (The engine chip and the Settings drawer), and its components under The editor in **Video Producer: technical reference**.

Cloud cost: PotionUI records the cost of every cloud job and shows it to admins only (Admin → Generations, and the spend statistics). For the estimate of Video Producer, see Generation › Cloud cost.

### Wan

- The preset defaults to 832×480 at 16 fps, which is also the default draft resolution of the plugin.
- PotionUI's hardware page lists Wan 2.2 14B (two experts) at 16 GB of VRAM or more, and the 5B variant as the realistic option for a small card (12 GB or more). Measured here, the 14B text-to-video and image-to-video pairs both run on a 12 GB card with about 35 GB of process memory (see Bench measures in **Video Producer: technical reference**), and the 1.3B and 5B run on an 8 GB card in the plugin's two 8 GB presets.

### LTX

- PotionUI's hardware page lists the LTX family as not yet recommended at any tier, because GPU validation is still open. LTX-2 and 2.3 are one all-in-one checkpoint of about 27 GB; LTX-2.5 uses separate files.
- On the 12 GB card of the Hardware measures, LTX-2.3 22B distilled fp8 ran out of GPU memory in the DiT at 832×480, for a 5-second and for a 2-second clip, with 62 GB of RAM. The plugin ships no LTX preset.
- LTX-2.5 22B distilled int8 ConvRot, with its Gemma4 int8 encoder, ran on that card for a text-to-video clip of 1 second at 480×832 with sound: 5 min 57 s from a cold start, about 1 minute of it for the 8 steps and the decode.
- On the same card, on 28 October 2026, without sound and in the Distilled recipe: a first-frame take at 768×448 over 121 frames ran 3.7 to 4.0 s a step, the same take made from a reference sheet 7.7 to 8.7 s a step, a sheet take at 832×480 over 73 frames 5.7 s a step, all with a peak of 11.8 GB on the card and no out-of-memory. The prompt encoder of LTX projects on the processor when the card is full, which adds 25 to 130 s a take.
- **License.** LTX-2.5 and its IC-LoRAs (Layout-To-Render, Ingredients) are published under the LTX-2.x Community License of Lightricks (11 August 2026), not an open-source license. It can be read at https://huggingface.co/Lightricks/LTX-2.5, the license address that the LTX-2.5 preset gives for its model files. The license says that below US$10M of annual revenue, the group counted, every use is allowed, commercial included, within its Attachment A and Lightricks' Acceptable Use Policy, and that above it a commercial license is needed. It also covers the consent of the real people a video shows or imitates, the transparency of generated content (its section 6 asks to say that a video is generated by AI where the law asks it, and to keep any watermark or marking), and competing products (Attachment A, point 20). The access form on Hugging Face also asks for consent to Lightricks' commercial offers, which can be withdrawn. PotionUI ships no weights.

### MiniMax-H3: read before enabling

Video Producer offers MiniMax-H3 as soon as its presets are installed and assigned, on the same footing as Wan. The interface shows no warning badge, so this reminder is for admins. The page writes the name of the model as **MiniMax H3** in the engine pop-up, on the take cards and in its messages (for example "MiniMax H3 only" next to the profiles that need it).

- **Validation status.** PotionUI's own documentation says that no end-to-end run on real weights has been performed for the MiniMax-H3 family, that GPU validation is pending, and that the family is not recommended on any card size until that is done. Video Producer does not change that status.
- **License.** The weights are published under the MiniMax H3 Community License, not an open-source license; the `description.md` of each MiniMax-H3 video preset sums it up. The license says that its Applicable Territory excludes the European Union, the United Kingdom, the United States and the Republic of Korea, that the exclusion extends to what the model generates, and that use there needs an individual authorization from MiniMax, applied for at https://platform.minimax.io/h3-license. It also says that a separate written authorization is required above US$20M of annual revenue, and that a commercial product's interface must display "MiniMax H3" prominently. The Fast and VDN variants carry the same terms. PotionUI ships no weights.
- **Files.** Four separate files are needed: the DiT, the text encoder, the video VAE and the audio VAE. The base MiniMax-H3 preset needs a fifth one for its **Upscale** mode, the latent upscaler; the sixth setup step lists all of them. The **Video Director** mode needs the `fl2va` DiT file and the **References to Video** mode the `ref2va` one. PotionUI cannot tell them apart, so check the file name: a wrong pick runs without an error and ignores the references. The Fast and VDN variants have neither a **References to Video** mode nor an **Upscale** mode (their finals go through SeedVR2).
- **Clips.** MiniMax-H3 runs at a fixed 24 fps, for clips up to 15 seconds; its release notes recommend 5 seconds or more. Picture and soundtrack come out of one pass. A shot longer than 15 seconds is cut and the estimate warns `duration_clamped`.
- **Hardware.** It is the heaviest family that PotionUI documents. If the card cannot hold it, the engine streams the overflow from host RAM, which is slower, and the production deck warns without blocking (see Generation › GPU memory in **Video Producer: technical reference**).

In Video Producer, the reference-guided profile (Ref2VA) uses the **References to Video** mode of MiniMax-H3. In Admin → Presets → Configuration, the MiniMax-H3 preset has tag filters for its DiT, text encoder and VAE pickers if you want to narrow the choices.

- **Name, `requires` and profile.** The name says the card; `requires` carries `min_vram_gb`, `recommended_vram_gb` (12 for the 8 GB presets, 16 for the Lightning preset) and `min_ram_gb`, which the preset picker shows as badges. `GET /me` gives every preset a `profile`, read from `vars.video_producer.profile`: `"8 GB · 32 GB RAM"` or `"12 GB · 64 GB RAM"` for these six, `null` for the others. The engine pop-up adds to the name the parts of the profile it does not already contain, so it shows **Wan 2.1 T2V 1.3B (8 GB) · 32 GB RAM**. The tags start with the card (`8gb` or `12gb`), `low-vram` and the RAM (`ram-32gb` or `ram-64gb`).
- **The engine settings.** No preset and no recipe can set the engine: **Text Encoder Placement**, **GPU Max VRAM (GB)** and **Shrink bf16 models to fp8 at load** are settings of the native backend (Admin → Backends). These presets were measured with their defaults, **Text Encoder Placement** on `auto`, **Shrink bf16 models to fp8 at load** on **Auto** and **GPU Max VRAM (GB)** at the value PotionUI derives from the card, and they expect them.
- **The recipes.** Each one enables the HuggingFace provider, indexes the models already on disk, asks to download only what is missing (the consent window of Admin → Recipes), installs the preset and assigns it to the admin who runs it. The two 8 GB recipes then run a 1-second text-to-video clip with 10 steps, within the 5 minutes the recipe runner gives a first generation by default (measured: 3 min 30 s and 2 min 32 s for the whole recipe with the files present; the first generation alone, from a cold start with the engine told the card has 8 GB, took 64 s for the 1.3B and 111 s for the 5B on 23 October 2026). Three recipes cover Wan 2.2 14B: `vp-wan22-14b-lightning-12gb` for the Lightning preset, `vp-wan22-14b-lightning-i2v-12gb` for its image-to-video companion, and `vp-wan22-14b-i2v`, which installs the core Wan 2.1 / 2.2 preset with both 14B expert pairs (about 64 GB, of which 28.6 GB for the image-to-video pair) so that shots can start from a frame. The companion recipe lists the same image-to-video experts as `vp-wan22-14b-i2v` and the same text encoder and VAE as the Lightning recipe, with the same SHA-256: the planning step finds what is already on disk, so a file is never downloaded twice, and only the lightx2v 4-step image-to-video LoRA pair (2.45 GB) is its own. It runs no first generation: its preset starts from an image only, and the recipe runner has none to give it. The Lightning recipe and `vp-wan22-14b-i2v` run a 1-second text-to-video clip with 6 steps and give it more time with `smoke.timeout_seconds`: 600 s each (measured with the files present: 4 min 02 s for the Lightning check clip with nothing in memory yet; 2 min 51 s for the image-to-video recipe with the text-to-video experts already in memory). The two MiniMax-H3 recipes run no first generation: on a 12 GB card, loading MiniMax-H3 alone took more than those 5 minutes, so their test generation always timed out. They have no "Validate the pipeline" step: that step of the core builds a test form without a Video Director document, which every Video Director preset rejects (the core `wan22-starter` recipe stops there too). The MiniMax-H3 recipe accepts the DiT of Comfy-Org or of Wan2GP, whichever is already installed.
- **Docker Desktop on Windows.** WSL 2 gives Docker half of the host's RAM by default. To give PotionUI the RAM a preset needs, raise it in `%UserProfile%\.wslconfig` (`[wsl2]`, `memory=…`), then run `wsl --shutdown`.

**How they were measured.** The measures of these presets (method, RAM limits, times, VRAM and RAM peaks, the Wan 2.2 5B decode and the Wan 2.2 14B runs on 12 GB) are under Bench measures › Measures in the presets of the plugin in **Video Producer: technical reference**.

**What does not fit on 12 GB yet.** LTX-2.3 22B distilled: see LTX.

**Files.** Each model picker recommends one tier, recognised by SHA-256 or else by file name, so the Wan2GP name works before the catalog has hashed the file. The 8 GB presets recommend the 1.3B DiT (`wan2.1_t2v_1.3B_fp16.safetensors`) or the 5B DiT (`wan2.2_ti2v_5B_fp16.safetensors`, converted to fp8 when it loads on an 8 GB card), the fp8 UMT5-XXL text encoder and the matching VAE (`wan_2.1_vae.safetensors` or `wan2.2_vae.safetensors`). For the MiniMax-H3 presets the int4 `convrot_w4a4` DiT is not recommended: the native engine cannot read it.

- **The Lightning pair.** Wan 2.2 14B Lightning (12 GB) names its companion for the compositions it does not declare in `vars.video_producer.companions` (`i2v` and `flf`: Wan 2.2 14B Lightning I2V (12 GB)), and the companion names it back for `t2v`. The key sits in the plugin's own `video_producer` block and not in `video_director`, which the core reads as the Video Director contract of the preset. For each shot, `build_plans` reckons the composition the shot asks for (`t2v` without an image, `i2v` with a first frame or the last image of the previous shot, `flf` with a last frame too or when it keeps its framing); when the preset does not declare it and names a companion for it, the shot is planned on the companion, if the user may run it and it has every file: `shots[].preset_id` of the estimate and `preset_id` of the takes name the companion, its time is reckoned with its own measures, and its memory is previewed once as a preset of its own. The engine of the shot and of the project does not change. The project's size for the Lightning preset (`engine.sizes`) applies to the companion, and so do its seed and every option the project sets for it (`engine.options`) that the companion's form also has; an option the project sets for the companion itself (`engine.options` under the companion's id) wins over the Lightning one. The companion sets `vars.video_producer.listed: false`: `GET /me` returns it with `listed: false`, and the engine pop-ups of the project and of a shot and the preset list of the Edit Engine window leave it out, while the takes, the queue and a project or a shot that already names it still show it by its name. The engine pop-up lists the compositions of the companion with those of the preset (`director_modes` of `GET /me`) while the companion is available, so the shot editor and the chain switch do not say the preset generates from text only. The companion is a copy of the Lightning preset with the image-to-video experts and LoRAs shown and selected and the text-to-video ones hidden and empty; its 4 steps and CFG 1 are its own speed profile, and its sizes its own copy of the 540p list. Its Advanced tab is its own copy of the core Wan tab, without the comments, whose only change is the step count the Fast profile sets (4, where the core and the Lightning preset set 6): the Steps field takes its value from a reaction of that tab to the speed profile, not from `speed_profiles`, so a 4-step profile alone would still run 6 steps. The lightx2v image-to-video LoRA is made for 4 steps; a take on 12 GB (9 November 2026) found 4 and 6 steps alike to the eye, 6 steps with slightly wider motion and 22 to 29 % slower. To run the image shots of one project in 6 steps without changing the preset, set `engine.options` to `{"01M57QPEMDPKHHW83YSEYBN0X2": {"steps": 6}}` in the project document: the shots keep the Fast profile and its CFG 1 (the text-to-video shots keep their own 6 steps). Do not set `speed_profile` to `custom` there: the custom profile takes the step count and the CFG of the form, 30 and 5, unless the options give both, and a distilled LoRA burns its frames at CFG 5. A retry or a final render of a companion take is planned again from the Lightning preset that the companion names back for `t2v` and that names it in turn (`director.handing_preset`), so it keeps the project's size and options for the Lightning preset; a shot that no longer has an image then runs on the Lightning preset. When the companion is available but cannot plan an image shot (a `DirectorError` of its own plan, or a plan in a composition it does not declare), the shot runs on the Lightning preset from its text with `frame_models_missing` or `chain_models_missing`, whose `reason` gives the cause (the code of the error, or `mode_unsupported`).
- **The 8 GB presets.** They copy the pipeline of the core Wan 2.1 / 2.2 preset unchanged and follow its tabs: Generation and LoRA are their own copies, in which the i2v DiT pickers and the image to video LoRAs are hidden, and they read its SVI Pro tab, hidden too, and (for the 5B) its Advanced tab: the pipeline needs the hidden fields, and a hidden field is not required. Their shots last up to 5 seconds. For the 5B, its hidden i2v DiT picker recommends the same 5B file as its t2v picker, and its i2v low-noise picker recommends nothing, so an image shot needs no other file. Its `timing.one_frame_tail`, copied from the core preset with the rest of its Video Director block, makes the core carry one motion latent for it, the one-frame tail the 5B continues from. The 5B offers no 720p (see Bench measures › Measures in the presets of the plugin in **Video Producer: technical reference**). The engine samples every Wan model with a shift of 8.0 where the 5B's official setting is 5.0; the form does not expose the shift.
- **Settings of the MiniMax-H3 presets.** 832×480 (480×832, 960×544 and 544×960 are offered, and 1344×768 stays in the list), 124 frames (5.17 s at 24 fps), one clip, sampler Res multistep with the Simple scheduler, a keyframe detail budget of 1× the output area, and the engine's automatic memory handling. The base model runs 20 steps (the Custom speed profile; Quality and Turbo are still there), Fast its fixed 8. For the sizes Video Producer asks of them, see Generation › Formats and sizes in **Video Producer: technical reference**.
- **Files of the MiniMax-H3 presets.** Each one follows its core preset (`content/presets/marketplace/MiniMax-H3` or `MiniMax-H3-Fast`). The LoRA and Enhance tabs, the Sparse attention and Step cache sections of the Advanced tab (with, for MiniMax-H3-Fast (12 GB), its Sampling section) and the resolution lists are read from that preset through `{{ paths._shared }}/../marketplace/...`: the core gives a `children` path only `paths.preset` and `paths._shared`, so another preset's folder is reached from the shared one. The pipelines (the loader reads a mode's `pipeline.yml` from the preset's own folder), the Generation, References and Advanced tabs and, for MiniMax-H3 (12 GB), the Sampling section (`files/form/advanced_sampling.yml`) are copies that only change defaults and recommendations; `tests/plugins/marketplace/test_video_producer_manifest.py` compares them with the core preset, field by field. The `extend` modes of MiniMax-H3 (12 GB) and MiniMax-H3-Fast (12 GB) are not copies: their pipelines are the core's `extend` reduced to continuing after the source (`source_video_role: continue` with 5 latents of overlap, the size and the frames taken from the form, no `video_concat`, the gallery fed by the generator), which the same test checks against the core pipeline step by step, and their forms are their own (the preset's speed profiles and models, a **New frames** stepper instead of the core's added length, the source video without the core's direction), which `tests/test_preset_fixtures.py` holds the test doubles to. One other exception: the **References to Video** mode of MiniMax-H3 (12 GB) has a **Reference image short edge** field (`reference_short_edge`, 1088 by default) that the core preset does not have, and its pipeline hands it to the generator's `reference_short_edge`, so that Video Producer can size the reference photos of each take (see Generation › How a take is made, point 4, in **Video Producer: technical reference**). The **References to Video** mode of MiniMax-H3 (12 GB) has its own Advanced tab, as in the core, on the same Sampling section as its **Video Director** mode (20 steps, Res multistep), and recommends the int8 ConvRot Ref2VA DiT. The Clip length field is in seconds, like every other duration of PotionUI: the pipeline turns it into frames at the model's fixed 24 fps, and the generator rounds up to its next count of 17n+5 frames; only the 15-second ceiling is a technical limit. The preset files carry no comments: what they would say is here and in the `description.md` of each preset, which also states the licence of the weights.
- **Prerequisites.** The 32B text encoder alone (14.6 GB in nvfp4) is larger than the card. The native backend option `text_encoder_placement` (**Text Encoder Placement**) was delivered by the core change "Stream the text encoder from host RAM when it does not fit in VRAM" (PotionUI/PotionUI#23, part of PotionUI) and ships with PotionUI's native memory profiles: leave it on `auto`, which streams a text encoder that does not fit from system RAM, or set it to `stream`. Without that option the presets load but the text encoder still runs out of GPU memory before sampling starts. The streamed encoder, the part of the 20 GB DiT that does not fit on the card and the rest of the process share the system RAM: `requires` declares 12 GB of VRAM (minimum and recommended) and 64 GB of RAM.
- **Speed.** Everything that does not fit on the card streams from system RAM, so expect the prompt encoding and every step to take noticeably longer than on a card that holds the model, or than on a 24 GB card; the 8 steps of MiniMax-H3-Fast (12 GB) keep its sampling short. The estimate warns `vram_stream` and does not block. The times measured on a 12 GB card are under Bench measures in **Video Producer: technical reference**.

### SeedVR2 for finals

- Making a take final upscales it: with SeedVR2 (its `video_upscale` mode) for a Wan, LTX, MiniMax-H3 Fast, MiniMax-H3 VDN, 12 GB MiniMax-H3 or cloud take, to 720p, 1080p, 1440p or 2160p (shown as 4K), and with the upscale mode of its own preset for a take of the base MiniMax-H3 preset. The targets, the other choices of the **Final render** window and the request of each are under Generation › Final takes in **Video Producer: technical reference**.
- The DiT comes in four sizes: 3B fp8 (3.39 GB), 3B fp16 (6.78 GB), 7B fp8 (8.24 GB) and 7B fp16 (16.48 GB), plus a VAE of about 501 MB. SeedVR2 also needs a prompt embedding file. PotionUI's hardware page says it scales down cleanly to small cards: the batch size follows about 72 % of the free VRAM and is halved on an out-of-memory error.
- When no upscaler is assigned to a user, the Upscale choice of the Final render window shows **Upscaler not available** and only the re-render is offered. A take of the base MiniMax-H3 preset still upscales, because its preset has an `upscale` mode; for the Fast and VDN variants and the 12 GB presets, which have none, see `upscale_unsupported` under Generation › Blocks and warnings in **Video Producer: technical reference**.
- Time: on the 12 GB card of the Hardware measures, the upscale of a 5-second Wan draft to 1080p took more than two hours (see Bench measures in **Video Producer: technical reference**). Plan quotas and expectations on that scale.

### RTX Upscale for finals

- The NVIDIA RTX Upscale plugin (`nvidia-rtx-upscale`) ships the preset **RTX Upscale** (`01KXRTXUPSCALE0000000000RU`). Its `video_upscale` mode runs NVIDIA RTX Video Super Resolution frame by frame on the Tensor Cores: a few seconds for a take, under 1 GB of VRAM, faithful to the take, and it adds no detail of its own. The plugin of PotionUI calls the `nvvfx` module of the `nvidia-vfx` package and ships nothing of NVIDIA; the administrator installs that package on the server, under NVIDIA's own licence.
- Video Producer offers it as **Fast (RTX)** in **Final render** and in **Final render of the film** when it is ready for the user (`GET /me` › `features.upscalers.rtx`): the preset is assigned, its `video_upscale` mode has a `target_short_side` field, and `nvvfx` can be imported on the server. The request it sends, the kind of source it is tuned for and when **Automatic** takes it are under Generation › Final takes in **Video Producer: technical reference**.
- Its `interpolate` mode runs NVIDIA Video Frame Generation, which Video Producer takes to conform the takes slower than the film when it is ready (see Generation › The frame rate of the takes in **Video Producer: technical reference**).

### Cloud presets

- **OpenRouter Video** and **Gemini Video** come with their provider plugins. Install and assign them like any other preset, and turn on a video model in the backend's catalog. The page lists each enabled model by name under its backend.
- Their resolution, duration and aspect ratio come from the parameters that the model declares (see Generation › Formats and sizes, and `no_model` under Generation › Blocks and warnings, in **Video Producer: technical reference**).
- The preset is tied to a backend through its driver. `GET /me` gives each preset its `driver` and, for a cloud preset, `backend_id`, the first enabled backend with that driver.

## Generation

The time measures of the plugin and how the estimate reckons a time from them, and the memory preview of the estimate and what the engine needs to stream the overflow, are under Generation › Time calibration and Generation › GPU memory in **Video Producer: technical reference**.

### Required models

For each `model` field that the chosen mode of the preset requires, Video Producer takes the first recommended file of the preset that is installed and reachable, and passes it as `model:<id>`. The recommendations are matched by SHA-256, and else by file name: when a preset gives no SHA-256 (the SeedVR2 case) or the catalog has not hashed the file (the Wan2GP DiT of MiniMax-H3 (12 GB)). A field with no installed recommendation blocks the generation with `missing_models`, and `data.fields` lists the fields. The fields are:

- Wan: `text_encoder`, `vae`, then `t2v_high_noise_model` (and `t2v_low_noise_model` when it is installed) for text-only shots, `i2v_high_noise_model` (and `i2v_low_noise_model`) for first-frame and first-and-last-frame shots. The default LoRAs of a form follow the same split: a text-only shot resolves the `t2v_loras_…` pickers alone, a first-frame shot the `i2v_loras_…` pickers alone, so a missing image-to-video LoRA never blocks a text-only shot. When the image-to-video set of a preset that also runs text to video is incomplete while its text-to-video set is complete, a shot that starts from an image runs from its text instead of being blocked (`chain_models_missing`, `frame_models_missing`).
- MiniMax H3: `model`, `text_encoder`, `video_vae`, `audio_vae`. The upscale mode of a final of the base MiniMax-H3 preset also needs `upscale_model`, which the sixth setup step checks too.
- SeedVR2: `diffusion_model`, `vae`, `prompt_embedding`. These are also the files of the finals of Wan, LTX, MiniMax-H3 Fast and VDN and cloud takes.

A file that exists on this machine but not on the Studio server worker passes the check and then fails on the worker (see Troubleshooting).

### Cloud cost

For an admin and a cloud model, the server asks PotionUI for the cost of the shots (`estimate_cloud_cost`). The prices are those of the catalog of the backend, filled in by the provider plugin. When the provider publishes no price for the model, `known` is false and the page says "Cost: unknown for this model". The cost is computed in the name of the admin who calls the estimate; a user who is not an admin gets `cost: null`. For the limit of the spending, see Quotas.

## ffmpeg

Video Producer calls `ffmpeg` and `ffprobe`, as found on the `PATH` of the PotionUI process, for four things:

- **The assembled video.** ffmpeg joins the shots, the sound and the look of the sequence into an intermediate file, then a last ffmpeg run writes the file that the user downloads (see Exports › The assembled video in **Video Producer: technical reference**). ffmpeg needs the `libx264` and `aac` encoders, `prores_ks` for the master and `libx265` for the archive, and the filters of the console (`equalizer`, `lowshelf`, `highshelf`, `lowpass`, `acompressor`, `pan`, `afir`, `aecho`). The plugin's tests ran with ffmpeg 6.1, 8.0 and 9.0, and the export reads its filter graph with the option that the version of ffmpeg knows (see Exports › The assembled video in **Video Producer: technical reference**); a build that lacks a filter or an option of the graph (for example `colortemperature`, or `normalize` of `amix`) fails the job with `ffmpeg_failed` and the message of ffmpeg.
- **A frame at a given time.** "Extract a frame at the playhead" asks for the frame at a number of seconds, and PotionUI reads the frame rate of the take with ffprobe to turn that time into a frame number. Without ffprobe the route answers 502 `extract_failed` ("The video's frame rate could not be read"). Without ffprobe the video export also treats every shot file as silent, because it cannot tell whether a file has a soundtrack: only the audio items of the timeline are mixed.
- **The sound of a shot.** A reference track, or the mix laid onto a LTX or MiniMax-H3 take, is cut with ffmpeg when the takes are created (see Generation › The sound of a shot in **Video Producer: technical reference**). Without ffmpeg such a shot is blocked with `audio_ffmpeg_missing`. A reference video track is cut with ffmpeg too, and without it a shot that sends one is blocked with `video_ffmpeg_missing`.
- **The last image of the previous shot.** A shot that starts from the last image of the previous one (see Generation › Chained takes in **Video Producer: technical reference**) needs ffmpeg once that image is taken, after the previous take has rendered. Without ffmpeg the estimate blocks such shots with `chain_ffmpeg_missing` (their ids in `shot_ids`), so that nothing is rendered that the chain could not continue.

How the install is checked and shown:

- The fifth setup step (`FfmpegReady`) is done when `ffmpeg` and `ffprobe` are both found (ffprobe next to ffmpeg, else on the `PATH`). While it is not done it says "Video Producer joins takes and exports the cut with ffmpeg, and reads media with ffprobe; ffmpeg is missing." (or "ffprobe is missing") followed by "Install ffmpeg with ffprobe on the server so both are on the PATH, then restart PotionUI." and offers **Read the guide**, which opens the administration page.
- `GET /me` carries `ffmpeg` (see Exports › Routes in **Video Producer: technical reference**). When it is `false`, the export window disables **Export** and says why (see chapter 14, Video, in **Video Producer: complete reference**), and the server refuses a video export by itself with 409 `ffmpeg_unavailable`. The files for other software, the subtitles and the frame extracted at the playhead work without ffmpeg; the first frame taken from the end of the previous shot needs it (503 `ffmpeg_missing`).
- The official PotionUI Docker image ships ffmpeg and ffprobe.

## Storage and exports

- The videos and their stems are written under `video_producer/exports/`, and the web and social videos are copied to the library of the user; the other exports are built at each download and stored nowhere. See Exports › Storage and quota in **Video Producer: technical reference**.
- Every work file of the plugin lives under `<file storage directory>/video_producer/` (`backend/workdir.py`): `exports/<user>/<job>/` for the exports, `frames/<user>/` for the frames taken from the shots, the images measured for the looks and the copy a guided final probes for the sound of its draft, `audio/<user>/` for the sound cuts, `writer/<user>/` for the reduced copies of the frames that the writing of a prompt sends. That folder must be local and writable even when the media are kept in object storage: the files the plugin reads from the storage are streamed into it (`local_media_file`), and the exported videos stay there. A folder that cannot be created or written is reported by the setup check `WorkFolderReady`, and at work by the code `workdir_unwritable`: an export job fails under it, the last image of the previous shot answers 503 `workdir_unwritable`, a sound cut refuses the request with 409 `blocked`, a guided final is blocked, and a look is marked failed with the message.
- Takes are ordinary PotionUI generations: their files and thumbnails stay in the user's history and gallery, under the user who owns the project, and the page plays them from `/api/media/generations/<generation id>/<file name>`. Deleting a take, or its project, in Video Producer does not delete the generation or its files. A user who deletes the generation from the gallery breaks the playback of the take.
- Projects are rows of the database, not files (see Projects and media › Tables in **Video Producer: technical reference**). Imported media are not copied: a project keeps a reference to the library item or to the generation file.
- Seam frames and the copy of each export are library items of the user, and count in that user's storage plan.
- **Import a cut as shots** uses the `cut_finder` media tool of PotionUI, which runs with ffmpeg on the processor, without the graphics card. Each search counts in the limit of 8 media tool runs waiting per user, and the pieces it makes are library items of the user, counted in that user's storage plan. There is nothing to set.
- Earlier versions wrote the splat files of the former Reframe from 3D tool under `video_producer/scenes/<project id>/`. Nothing reads, writes or deletes that folder any more: an administrator can delete it by hand.

## Projects and media

### Versions and the `versions_kept` setting

Each save that changes the document adds a row to `video_producer_versions` with the next version number and updates the project row. The page saves by itself after each change (see chapter 5, Saving, in **Video Producer: complete reference**), so one editing session produces many versions.

**Versions kept per project** (`versions_kept`, 5 to 500, default 50) caps the history. After every save and every restore, a project keeps its most recent N versions and the older rows are deleted; the current version is always one of them. Lowering the setting takes effect at the next save of each project. Every version holds the whole document (at most 4 MiB), so a project can use about N times the size of its document. Restoring a version that was pruned answers 404 `version_not_found`.

A restore never rewrites history: it stores the restored document as the next version, checked as a save is (see Projects and media › Routes in **Video Producer: technical reference**), and it is pruned like any other save.

### The starter project

The page creates it when the user has no project. How it is built, what it holds and what each engine makes of it are under Projects and media › The starter project in **Video Producer: technical reference**; the provenance of its three images is under Licenses below.

### Access

A project belongs to the user who created it, and every route checks it.

- The list shows only the caller's own projects, admins included.
- Reading, saving, deleting, listing the versions, restoring, and every route of the takes, the estimate, the generation, the exports and the seam frame need the project to be the caller's, or the caller to be an admin. For anyone else the answer is 404 `project_not_found` (or `take_not_found`, `job_not_found`), never 403, so the existence of a project is not revealed. An admin who knows a project id can therefore read or change any project through the API, and start takes on it: they run as the owner of the project, with the owner's presets, quota and history. An admin who exports a project gets the job, the folder and the library copy under their own account, with the media resolved as the owner; a seam frame is stored in the owner's library. The page offers no way to list the projects of other users.
- `PUT /me` accepts only the caller's own projects as `last_project_id`, admins included.
- `POST /media/resolve` resolves only what the caller can read in PotionUI: their own library items and the generations that are visible to them.

## Notifications

Video Producer sends a PotionUI notification to the owner of a take when it is ready (**Video Producer: take ready**, type `video-producer.take_done`) and when it fails (**Video Producer: take failed**, type `video-producer.take_failed`). The text reads "<project name>: the draft take A is ready." or "<project name>: the final take B failed." followed by the reason, and carries `project_id`, `take_id` and `shot_id` as metadata. Both types are on by default, and each user can tune them in their notification preferences. The page also shows a toast when the takes it follows end ("2 draft takes ready", "1 take failed").

A video export sends its own two notifications to the user who asked for it: **Video Producer: export ready** (`video-producer.export_done`) and **Video Producer: export failed** (`video-producer.export_failed`). Both are on by default and tunable like the first two; their text and metadata are described under Exports › The assembled video in **Video Producer: technical reference**.

## The assistant mode

### Requirements

- **A language model, configured and assigned.** In Admin → LLM / Assistant, click **Add configuration**, pick a type (OpenAI for a local llama.cpp `llama-server` or an online provider, or Ollama with its settings adjusted, see Which language model), then assign the configuration to the users or groups who use Video Producer. The plugin calls no model itself: the chat uses the model that PotionUI gives the user, like for every other chat mode. Without an assigned configuration the chat is empty: an admin reads "No enabled LLM configurations", a user "Chat is currently unavailable".
- **A model that can call tools.** Every action is a tool. A model that cannot call them only answers in text.
- **Tools on.** In the composer of the chat, **Tools** must be on (its tooltip reads "Tools ON" or "Tools OFF"). An admin can also turn a tool off, or lock it on, for one configuration: Admin → LLM / Assistant, open the configuration, tab **Toolset**, group **Video Producer**.
- **Where the text goes.** The context block described below is sent to the model with every message. With a hosted provider such as OpenAI it leaves your server for that provider; with a model that runs on your own machines (Native, or a llama-server or Ollama that you host) it does not.

### Which language model

The chat sends the context block and the definitions of the tools with every message (under a context window of 24,576 tokens, the production tools only on demand: see The assistant mode › Tools sent up front in **Video Producer: technical reference**), and the tools only work when the model calls them correctly. The model must also fit in memory next to whatever else runs on the machine. There are two local options, plus the online providers. Both local engines were measured on the RTX 4070 Ti 12 GB, with real conversations of the assistant and the real OpenAI-type and Ollama-type clients of the PotionUI core. With the same settings they run at the same speed, because Ollama 0.30 and later runs the `llama-server` of llama.cpp itself: for Qwen3-8B Q4_K_M, about 5,000 tokens/s of prefill and 74 tokens/s of generation, and a tool turn takes 0.5 to 7.7 s.

- **Recommended when the model shares the video card: llama.cpp `llama-server`, added as an OpenAI configuration.** It reserves its memory at load time, unloads on demand and takes an API key.
- llama-server, simple mode, one model:

```
llama-server -m Qwen3-4B-Q4_K_M.gguf -a qwen3-4b -c 16384 -ctk q8_0 -ctv q8_0 -np 1 --reasoning off --host 127.0.0.1 --port 9931 --api-key-file llm-keys.txt --sleep-idle-seconds 60
```

`-a qwen3-4b` names the model; `-c 16384` opens a context of 16,384 tokens; `-ctk q8_0 -ctv q8_0` keeps the KV cache in q8_0, about 1.1 GB less than f16 at that size; `-np 1` opens a single slot; `--reasoning off` turns the thinking of Qwen3 off on the server; `--host 127.0.0.1` listens locally; `--api-key-file` reads the API keys from a file, one per line; `--sleep-idle-seconds 60` puts the server to sleep after 60 s without a request, which frees its VRAM (measured with Qwen3-8B: about 6.9 GB freed, and the next request woke it in about 2 s).

- llama-server, router mode, to unload on demand:

```
llama-server --models-preset models.ini --models-max 1 --host 127.0.0.1 --port 9931 --api-key-file llm-keys.txt
```

In router mode, llama-server reads a preset file of this form:

```ini
[qwen3-4b]
model = /models/Qwen3-4B-Q4_K_M.gguf
ctx-size = 16384
cache-type-k = q8_0
cache-type-v = q8_0
parallel = 1
```

Before a video generation, `POST /models/unload` with the body `{"model": "qwen3-4b"}` unloads the model (measured: 1.0 s, VRAM back to its base level); the next chat request loads it again by itself (2 to 3 s). PotionUI has no action for this call yet: send it, with the header `Authorization: Bearer <key>`, from your own script or scheduler.

- The default port of llama-server is 9931 since llama.cpp v0.7.0 (8080 in its Docker images).
- In PotionUI, Admin → LLM / Assistant → **Add configuration**, with these fields for llama-server:
- type **OpenAI**;
- **Base URL** `http://127.0.0.1:9931/v1`, or `http://host.docker.internal:9931/v1` from the PotionUI Docker image under Docker Desktop. Under Docker on Linux, start the container with `--add-host=host.docker.internal:host-gateway` and make llama-server listen beyond 127.0.0.1 (`--host 0.0.0.0`), hence the API key;
- **API Key**: a key of the file;
- **Model**: the name given by `-a`, or the section name of the preset file (`qwen3-4b`); the model discovery of the form lists them;
- under **OpenAI Options**, **Reasoning Effort** **None**. Otherwise Qwen3 thinks before every call: a turn takes about 14 s instead of 1 to 2 s, and the thinking can use up **Max Tokens** without calling a tool;
- under **OpenAI Options**, **Context window** = the value of `-c` (16384), so that the chat budgets the conversation to what the server accepts.
- **Ollama works once three settings are made under Ollama Options.** Without them the assistant does not work.
- Ollama, **Context Size** 16384 or more. Left empty, Ollama opens its default context, 4,096 tokens on a card under 24 GB, and every turn of the assistant is refused with "Ollama returned status 400: request (… tokens) exceeds the available context size (4096 tokens)": the first turn already takes about 4,800 tokens.
- Ollama, **Keep Alive** between 5m and 30m. The PotionUI default is 0: the model is unloaded after every answer and loaded again at every turn, which adds 4.5 to 6 s.
- Ollama, **Thinking Mode** **Automatic** (it turns thinking off when tools are sent) or **Disabled**.
- Ollama has no authentication: leave it on 127.0.0.1.
- Ollama, to free the VRAM before a generation: the quick action **Clear Ollama VRAM** of the Ollama plugin, or the automation template **Free VRAM before a generation (automatic)**.
- **Measured models**, each with every tool call correct (8 of 8, or 6 of 6):
- Measured models, Qwen3-4B Q4_K_M when the video shares the card: about 3.9 GB of VRAM with the q8_0 KV cache at 16,384 tokens, 0.3 to 5.5 s per turn;
- Measured models, Qwen3-8B Q4_K_M otherwise: about 6.0 GB with the q8_0 KV cache, 7.1 GB in f16, 0.5 to 7.7 s per turn.
- Measured models: in both engines the VRAM does not grow while a long prompt is processed: the memory is reserved at load time, and a prompt that is too long is refused instead of running out of memory.
- **Unload before a video generation, whichever the engine.** Under native Windows an overlap gives no error but silently slows one of the two processes (measured: −50 % on prefill). Under Docker or Linux, a CUDA out of memory error from the video engine is likely.
- **An online provider** (OpenAI or another) stays possible and leaves the whole card to the engine. It was not measured: the assistant was validated end to end against a scripted OpenAI-compatible server (mode, context, tools, approval cards, writes, page updates). Whatever you pick, check one conversation with the model you choose, and pick a model that supports tool calls.
- **Not recommended on a 12 GB card: the Native client.** Measured on the RTX 4070 Ti 12 GB, with the tools sent as part of the prompt (`force_prompt_tools`):
- Native client, Qwen3 4B in nf4 loads (129 s the first time, about 4.4 GB of VRAM for the model) and answers a short question, but the first real turn of the assistant ran out of GPU memory while the prompt was processed: peak 11,971 MiB, CUDA out of memory after 91 s, no tool called. With the thinking mode of the model on, the turn had not ended after 12 minutes. The context block is not the cause (about 1,500 characters for a project of four shots): the native client does not bound its attention memory while it processes the prompt. After the error the CUDA context of the PotionUI process stayed unusable, so every following turn failed within seconds until the container was restarted.
- Native client, Qwen3 1.7B in nf4 loads in 29 s (about 2.6 GB) and never ran out of memory (peak 4.6 GB), and its turns lasted 5 to 91 s, but it produced one well-formed tool call in nine attempts and no approval card: it is too small for the tool protocol.
- The `nf4` and `int8` quantizations of the Native client need the optional Python package `bitsandbytes`, which the PotionUI image does not contain. The 4B model without quantization (bf16, 7.5 GB) did not fit either.

## Troubleshooting

What the user sees and does in each case is in chapter 17, Troubleshooting, of **Video Producer: complete reference**, and in its chapter 10 for the assistant.

- **No engine in the production deck**: the first setup step is not done, or the backend is turned off, or no video preset is assigned to the user, or a cloud backend has no video model turned on in its catalog. ComfyUI backends are never offered. The pop-up says "No engine" and, for an admin, links to the plugin settings (**Open plugin settings**).
- **The estimate shows "—" for the time**: no timing has been measured yet for this preset, engine and resolution on this machine (the calibration table has no row for them). It fills in after a few generations.
- **"Will stream through host RAM, slower"**: the estimated memory is above what the engine has. The generation is not blocked. Check the VRAM cap of the backend (`gpu_max_vram`, Admin → Backends); if the server lacks free RAM for the overflow, the engine refuses to start and the take fails with `host_ram_oom`.
- **A submit is refused for a limit** (409 `blocked`, block `quota_exceeded`): the user reached the monthly **Video Producer GPU minutes** set in Admin → Users → Plans. Takes in flight and takes waiting for a place count with their reservation; failed and cancelled takes are refunded. Until a preset has been measured, each second of video reserves 10 seconds of GPU, so the quota can look consumed faster than the real runs (the adjustment at the end of each take corrects it).
- **Generate selection is disabled**: there is no valid range, or no direction and no shot prompt in the range, or a prompt is empty, or the engine is gone or missing, or the server reports a block (the deck shows the first one): missing models ("Models to install for this preset: …", to download in Admin → Downloads or Admin → Models), a profile the preset cannot generate, a cloud model to pick, a quota spent. The rules are applied on the server too.
- **A take stays Queued**: a take past `max_parallel_jobs` waits for a place, and the user's other takes, in every project, have to end first. The generation queue (the queue button of the production deck) shows its place and the slots; **Move to the head of the queue** makes it the next one handed over. Look at `GET /projects/{id}/queue` (`queue_position`, `slots.in_flight` against `slots.max`, `elsewhere`) and raise **Max generations in flight per user** if the machine can take more. If nothing is in flight, check that the follow-up task is running: the server log shows "[VIDEO-PRODUCER] Take tracker started" after the application is ready, and the next generation starts it again. A take that is also Queued in PotionUI's own queue stays Queued here until its generation runs.
- **A take failed with `missing_model_file`**: a model file that the preset needs is not where PotionUI looks for it. Re-download it in Admin → Downloads or Admin → Models, and check that it was not moved or deleted. For a Studio server, the file must be on the worker too: the plugin only checks the files of this machine.
- **A take failed with `cuda_oom`**: the card ran out of memory. The memory estimate is a lower bound and only warns. Lower the draft resolution (**Draft resolution**), use a shorter shot, close the other applications that use the GPU, or switch to a lighter preset or a cloud model. If every take then fails within seconds, see Every take fails within seconds after an out-of-memory error below. `host_ram_oom` is the same problem on the host RAM that streaming needs.
- **The Upscale choice says "Upscaler not available"**: no SeedVR2 preset is assigned to the user (third setup step), or its model files are missing. A take of the base MiniMax-H3 preset does not depend on SeedVR2, but on its own latent upscaler file (sixth setup step). A final that fails to start with `missing_models` names the SeedVR2 fields (`diffusion_model`, `vae`, `prompt_embedding`) that have no installed file.
- **An upscale or a conform works for an administrator and not for a user**: SeedVR2, RTX Upscale or Video Tools is installed but assigned to no one, which only an administrator can use (see the third step under Setup checks), so the user reads "Upscaler not available" or "No interpolator is ready: install Video Tools with RIFE 4.25 so the export stops repeating frames." where the administrator reads nothing. The third setup step names the presets in that case and offers **Assign SeedVR2**, or **Assign RTX Upscale** when SeedVR2 is not installed.
- **References are ignored in a MiniMax-H3 run**: the `fl2va` DiT file was picked for the **References to Video** mode (see the reminder above).
- **A take failed after PotionUI restarted**: a generation that was running when the server stopped is marked failed and cannot resume.
- **The export window says "ffmpeg is missing on the server: video exports need it."** (or a request answers 409 `ffmpeg_unavailable`): `ffmpeg` is not on the `PATH` of the PotionUI process. Install ffmpeg and ffprobe, make sure that process sees them, and restart PotionUI (see ffmpeg); the fifth setup step turns green and `GET /me` answers `ffmpeg: true`. The page reads `ffmpeg` when it opens.
- **"No shot has a video file to export yet."** (409 `nothing_to_export`): no shot of the saved project has a file the server can find, for example because every shot is still "To generate", or the imported media were removed from the library or the gallery. A single missing shot does not stop an export: it is black in the video.
- **"An export of this project is already running."** (409 `export_running`): a project has one export in flight.
- **"The export folder is full: delete older exports and try again."** (429 `export_quota`): the folder of the user is over **Export cache per user (MB)** and nothing finished can be evicted, so the space is held by a job that is queued or running. Raise the setting, or wait for that job.
- **An export stays Queued**: the server runs one export at a time, whoever asks, so it waits for the others. If nothing runs, the runner did not start: look for "[VIDEO-PRODUCER] Could not start the export runner" in the server log; the next export request, or a restart, starts it again.
- **An export moves slowly through "Converting to MP4"**: the delivery run uses the `slow` preset, and on a small server a long 4K sequence takes long; the progress shows how far it is. It fails with `transcode_failed` only when ffmpeg writes nothing for 5 minutes. Export at 1080p or 720p to go faster.
- **An export fails with `ffmpeg_failed`**: the message under the failure is the last line of ffmpeg's error output. Typical causes: a source file ffmpeg cannot read, an ffmpeg build without a filter or an encoder of the graph (see ffmpeg), or a restart of PotionUI during the export ("The server stopped during the export.").
- **A done export leaves `mezzanine.mkv` or `graph.txt` in its folder**: another program (an antivirus or the indexer) held the file open while the server tried to delete it. Nothing to fix: the next export request of that user, or the next start of the server, sweeps it (see Exports › Storage and quota in **Video Producer: technical reference**).
- **Cancelling an export leaves ffmpeg running**: the server kills the whole process tree, so the real ffmpeg behind a launcher, such as the `ffmpeg.exe` shim of a package manager, stops with it. If one stays, check that `psutil` is installed in the Python environment of PotionUI (it is in `requirements.txt`).
- **The first setup step says "Takes cannot run on This machine: no GPU is configured."**: the native backend is set to `cpu`, which PotionUI reports as having no GPU, so takes cannot run on it. Set a CUDA device in the backend (Admin → Backends), or use a Studio server or a cloud model.
- **The first setup step says "Takes cannot run on This machine: no GPU could be read for it"**: the native backend is set to a `cuda` device but PotionUI could not read a GPU for it: the host has no CUDA (the `remote` profile), the NVIDIA driver is broken, or the device has no explicit ordinal on a host with several cards. Fix the driver, set `cuda:0`, or disable the backend on a host without a GPU and use a Studio server or a cloud model; otherwise the takes fail when they run.
- **A setup step says "Video Producer cannot write in …"**: the file storage directory is missing, read-only or not a directory, so the plugin cannot make its work files. Set a writable local folder in Admin → Settings, or mount one into the container; with object storage the media stay there, only the work files need the folder.
- **A take card says Not cropped** (`frame_not_cropped`): the crop of a start or end image could not be made or stored in the library of the owner of the project, so the take went with the original picture, which may come out stretched in the take, depending on the engine and the version of PotionUI. Its tooltip, and the `cause` of the note, say why: `storage_full` (the storage plan of that user is full), `upload_too_large` (the crop is larger than the largest upload of that user), `too_many_pixels` (the picture has more than 64 million pixels) or `failed` (anything else, the details in the server log); how the crops are made is under Generation › Start and end images in another ratio in **Video Producer: technical reference**. Free some space, raise the limit, or give the shot an image in the frame of the take, then make the take again.
- **An export fails with `store_failed`**: the web or social MP4 was made but PotionUI refused to store it in the library of the user, for example because the storage plan of that user is full, or the ZIP of the stems could not be written (a full disk). Free some space and export again.
- **A shot is black, or has no sound, in the video**: a shot with no file the server can find is black and silent (see "Which file a shot has" under Exports › Files for other software in **Video Producer: technical reference**). A shot whose file has no soundtrack is silent too, and so is every shot when ffprobe is missing.
- **The sound differs from the console**: the export plays the console as the page does (see Exports › The assembled video in **Video Producer: technical reference**), except the look-ahead and the release curve of the browser's compressor, so a compressed track can differ on its attacks, and the echoes of the delay below −60 dB. The levels are added without automatic leveling, so loud tracks can clip; a mono file is as loud on each channel as the page plays it, 3 dB above ffmpeg's own up-mix.
- **An FCPXML, OpenTimelineIO or EDL file does not find its media**: the paths in the file are paths on the PotionUI server. The files of generated takes are all called `1.mp4`; the folder tells them apart.
- **"This export no longer exists." or "The video is not ready yet." when downloading**: the export was deleted or evicted to make room, or it is not finished.
- **A seam frame is refused**: "This shot has no previous shot." (the first shot cannot use one); "“Shot” has no take or video yet." or "The previous shot has no take or video to take a frame from." (409 `no_media`: nothing is placed on the previous shot, or its file is gone); "ffmpeg is missing on the server: the last frame cannot be taken." (503 `ffmpeg_missing`); "The previous shot has no finished take with a file." (409 `no_previous_take`, for a frame at the playhead); "The image could not be extracted from the take." (502 `extract_failed`: read `detail.data.code` in the network tools, `limit_exceeded` meaning that the storage plan of the project owner is full, and a frame at a given time also fails without ffprobe); "This shot is not in the saved project." (404 `shot_not_found`: save the project and try again).
- **A user's changes do not save ("Not saved — retry")**: read the answer of the failing `PUT /projects/{id}` in the network tools of the browser. 422 `invalid_doc` gives the path of the refused value (usually a tab opened before a plugin update: the user copies what they need, then reloads); 422 `doc_too_large` means the document is over 4 MiB; 409 `version_conflict` is handled by the page (see below); a 401 means the session expired.
- **"This project was deleted elsewhere"**: a save answered 404 `project_not_found` because the project had been deleted, from another tab or device or through the API. Nothing to fix: the page stopped saving it and opened the most recent project of the user, or created the starter project.
- **"Changes saved elsewhere were merged into the project"**: the same project was saved from another tab, window or device, or by the assistant, so the save of this page was refused with 409 `version_conflict` and the page merged the saved version with its own (see Projects and media › Concurrent saves in **Video Producer: technical reference**). Nothing to fix; the other versions are in the history. "Project reloaded: it changed elsewhere" means the page had nothing to merge with and dropped its unsaved changes.
- **A user cannot find an earlier version**: the history keeps only the **Versions kept per project** latest versions (50 by default). Raise the setting; versions already pruned do not come back.
- **Imported media do not show or play**: the library item or the generation was removed, so its URL no longer answers (and a new import of it answers 404 `media_not_found`). A take whose generation was deleted from the gallery no longer plays either.
- **A user sees the wrong language**: it is stored per user, and the user changes it in the page (see chapter 15, Language, in **Video Producer: complete reference**).
- **The chat says "Chat is currently unavailable" (an admin reads "No enabled LLM configurations")**: no language model configuration is enabled and assigned to the user. Add one in Admin → LLM / Assistant and assign it to the user or to a group (see The assistant mode › Requirements).
- **The assistant answers in text and never shows an approval card**: **Tools** is off in the composer of the chat (tooltip "Tools OFF"), or the tool is off for that configuration (Admin → LLM / Assistant, the configuration, tab **Toolset**, group **Video Producer**), or the model cannot call tools.
- **The assistant knows nothing of the project, or the chat header says "Started in …"**: the conversation was started in another mode and keeps it.
- **The assistant says the page is not open on a project**: the page sends its context only while it is open on a project, and a tool called without a project answers `project_not_found`.
- **A card shows Failed with `version_conflict`, `project_not_found` or `shot_not_found`**: the project was saved elsewhere at the very moment of the save, or was deleted, or the shot is no longer in the saved project (see The assistant mode › Errors in **Video Producer: technical reference**).
- **A change is approved and the page shows nothing**: the result was for another project (the chat shows "The assistant changed another project, not the one open here."). Nothing else to fix.
- **A suggestion opens the chat with an empty box**: the host has no `chat.prefill` (see The assistant mode › Suggestions and `chat.prefill` in **Video Producer: technical reference**), or the composer already held a draft, which is kept.
- **A shot says "Media offline"**: the page cannot play the file of that shot any more, because the library item or the generation file was removed, or the shot kept no source. The viewer shows "Media offline" and says that the source file of the media is no longer available (import it again or choose a take); the export looks for it again on the server (see A shot is black, or has no sound, in the video, above).
- **Every take fails within seconds after an out-of-memory error** (native engine, `gpu_restart_required`: "The server’s GPU needs a restart before it can generate again: an administrator must restart the backend (Administration › Backends)."): the CUDA context of the PotionUI process can stay unusable after a `cuda_oom` (seen on a 12 GB card, with MiniMax-H3 before the 12 GB presets and with the Native language model). Restart PotionUI (**Restart Backend** in Admin → Backends restarts it), then use the 12 GB presets or a lighter model (see Hardware).
- **The assistant ends with "CUDA out of memory" or never shows a card on the Native language model**: see The assistant mode › Which language model. Move the configuration to a llama-server or an Ollama set up as described there, or to an online provider.
- **Every turn fails with "Ollama returned status 400: request (… tokens) exceeds the available context size (4096 tokens)"**: the Ollama configuration has no **Context Size**, so Ollama opened its default context. Set **Context Size** to 16384 under Ollama Options (see The assistant mode › Which language model).
- **Every turn of the assistant is slow** (about 14 s instead of 1 to 2 s when the model thinks before each call; 6.5 to 14.5 s instead of 0.5 to 7.7 s when Ollama reloads the model at every turn): set **Reasoning Effort** to None for an OpenAI configuration, or **Thinking Mode** to Automatic or Disabled for Ollama, and set **Keep Alive** between 5m and 30m, since its default is 0.
